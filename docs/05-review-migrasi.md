## Temuan terkonfirmasi

### 1. [HIGH] publish_emission_factor leaks the revoked UPDATE privilege: no role check, no tenant check, caller-controlled valid_to, forgeable approved_by, and it corrupts the version timeline

**Lokasi:** `db/migrations/0014_core_fix.sql:187` · lensa `privilege-deadlock`

**Skenario kegagalan:** 0013_rls.sql:18 revoked UPDATE on emission_factors specifically to make MRV provenance append-only, and 0014 reintroduces an UPDATE with a caller-supplied predicate value (p_code) and a caller-supplied new value (p_valid_from - 1 day). Any holder of the app_rw connection — including a plain `viewer`, including a request with no session context at all, so nothing is written to actor_id — can (a) set valid_to on any active factor to any date, including before its own valid_from, breaking the "one active version, no gaps, no overlaps" invariant that carbon-run reproducibility rests on; (b) fabricate MRV expert sign-off by passing p_approved_by, which the function stores verbatim along with approved_at = now(); (c) insert negative factor values and blank names, while source_standard is the only field validated.

**Perbaikan:** In app.publish_emission_factor: (1) reject p_valid_from that is not strictly greater than the active version's valid_from (`SELECT valid_from FROM app.emission_factors WHERE code=p_code AND valid_to IS NULL`); (2) drop the p_approved_by parameter and derive it from app.current_user_id(), raising if it is NULL, and gate on the caller's role (`app.current_role_name() IN ('approver','super_admin')`); (3) validate p_value > 0 and non-blank p_name; (4) add `ALTER TABLE app.emission_factors ADD CONSTRAINT ef_valid_range CHECK (valid_to IS NULL OR valid_to >= valid_from)` as a belt-and-braces guard; (5) create a non-superuser owner role for the function (`CREATE ROLE app_ef_owner NOINHERIT; ALTER FUNCTION ... OWNER TO app_ef_owner;`) so SECURITY DEFINER does not mean superuser.

### 2. [HIGH] uca_self policy lets any app_rw session grant itself access to any company, voiding the multi-tenancy model 0014 introduced

**Lokasi:** `db/migrations/0014_core_fix.sql:414` · lensa `privilege-deadlock`

**Skenario kegagalan:** 0014:31-32 declares user_company_access "Sumber otorisasi tenant" (the source of tenant authorization). Because the write path of its own policy accepts a self-referencing row, the authorization table is self-service: any SQL injection, leaked connection string, or over-broad server action running as app_rw executes two statements — INSERT a uca row for itself, then read/write every block, cost transaction, budget, evidence file and approval of every other company. verify.mjs's "creator TIDAK bisa pinjam company B" check passes only because it never tries the insert. Combined with the un-RLS'd companies table, the same session can also create a company it then grants itself.

**Perbaikan:** Split the policy by command: `CREATE POLICY uca_read ON app.user_company_access FOR SELECT USING (user_id = app.current_user_id() OR app.company_in_scope(company_id));` plus a write policy that never accepts the self branch and requires an admin role, e.g. `CREATE POLICY uca_write ON app.user_company_access FOR ALL USING (app.company_in_scope(company_id) AND app.current_role_name() = 'super_admin') WITH CHECK (app.company_in_scope(company_id) AND app.current_role_name() = 'super_admin');` — and better, move the grant/revoke operation behind a SECURITY DEFINER function so it cannot be issued as raw DML at all. Separately, enable RLS on app.companies. Add a verify.mjs check that the self-grant INSERT is rejected.

### 3. [HIGH] Session bootstrap deadlock: app.users is unreadable until app.current_user_id is already known, and only app.users can supply it

**Lokasi:** `db/migrations/0014_core_fix.sql:340` · lensa `privilege-deadlock`

**Skenario kegagalan:** docs/01-desain-skema-database.md:1243-1246 specifies the app sets app.current_user_id per transaction from Identity Platform JWT claims. The JWT carries the IdP subject, which the schema stores as app.users.external_id (0002_core); app.users.id is a uuid generated by Postgres at insert time and is not a JWT claim. So every request must first run `SELECT id, company_id, app_role FROM app.users WHERE external_id = $jwt_sub` — which returns 0 rows, because that policy needs the id the query is trying to obtain. 0014 made this strictly worse than 0013: previously the lookup only needed current_company_id (a plausible claim); now it needs the internal uuid plus a user_company_access row. Result: no session can ever be established through app_rw; the only way past it is to run the lookup as a superuser, which is exactly the false-pass pattern the prior audit flagged.

**Perbaikan:** Add a narrow SECURITY DEFINER resolver owned by a non-superuser role with SET search_path, e.g. `CREATE FUNCTION app.resolve_session(p_external_id text) RETURNS TABLE(user_id uuid, company_id uuid, app_role app.app_role) LANGUAGE sql SECURITY DEFINER SET search_path = app, pg_catalog AS $$ SELECT id, company_id, app_role FROM app.users WHERE external_id = p_external_id $$;` then `REVOKE ALL ... FROM PUBLIC; GRANT EXECUTE ... TO app_rw;`. Alternative: add `CREATE POLICY users_self_lookup ON app.users FOR SELECT USING (external_id = NULLIF(current_setting('app.current_external_id', true), ''))`. Cover it in verify.mjs with a check that runs the lookup as app_user with no context.

### 4. [HIGH] The three built-in report definitions concept:70 requires are deletable and editable by any app_rw session, including a viewer

**Lokasi:** `db/migrations/0017_reports.sql:318` · lensa `privilege-deadlock`

**Skenario kegagalan:** concept:70 requires the three built-in reports to exist as three definition rows rather than three hardcoded pages, and 0017:32/40-41 makes is_stub the flag the UI must honour so unfinished reports are labelled honestly. A tenant-A user (or a bug in a tenant-scoped server action, or the self-service builder of phase 2) issues a DELETE or flips is_stub on the shared company_id-NULL rows, and every company's report list breaks or starts presenting an empty sustainability report as if it were real. The company_id IS NULL branch that makes global rows readable across tenants was reused verbatim for WITH CHECK, so read-everywhere silently became write-everywhere.

**Perbaikan:** Add a restrictive policy that keeps global rows read-only for app_rw: `CREATE POLICY rd_builtin_readonly ON app.report_definitions AS RESTRICTIVE FOR ALL USING (NOT is_builtin AND company_id IS NOT NULL) WITH CHECK (NOT is_builtin AND company_id IS NOT NULL);` (keep the permissive rd_tenant for SELECT via a separate FOR SELECT policy), and enable RLS with an equivalent policy on app.report_definition_fields, deriving the tenant through report_id. Add a verify.mjs check asserting the built-in DELETE is refused as app_user.

### 5. [HIGH] master_types.is_system is documented as undeletable but nothing enforces it — app_rw deletes system types, cascading away every dropdown value

**Lokasi:** `db/migrations/0015_master.sql:24` · lensa `privilege-deadlock`

**Skenario kegagalan:** One of the 10 seeded system master types (0015:53-63) is deleted by any app_rw session — a mis-wired delete button on the master-data CRUD screen 0015:48-49 describes as "satu screen", or a viewer-role account. ON DELETE CASCADE then removes all master_items of that type, and every row pointing at those items via ON-DELETE-restricting FKs (cost_transactions.cost_category_id, budgets.cost_category_id, land_suitability_assessments.soil_type_item_id, fertilizer_types.uom_item_id, ...) either blocks the delete with a confusing FK error or, where no such reference exists yet, loses the whole dropdown vocabulary with no way to recover it except a migration.

**Perbaikan:** Enforce the documented rule in the database: `CREATE FUNCTION app.guard_system_master_type() RETURNS trigger LANGUAGE plpgsql AS $$ BEGIN IF OLD.is_system THEN RAISE EXCEPTION 'master_type % adalah is_system dan tidak boleh dihapus', OLD.code; END IF; RETURN OLD; END $$;` plus `CREATE TRIGGER master_types_no_delete_system BEFORE DELETE ON app.master_types FOR EACH ROW EXECUTE FUNCTION app.guard_system_master_type();` (and the same guard on UPDATE of code/is_system). Consider revoking DELETE on app.master_types from app_rw entirely, since types are structure rather than data.

### 6. [CRITICAL] user_company_access is self-writable: any app_rw session can grant itself access to any company, defeating every tenant policy at once

**Lokasi:** `db/migrations/0014_core_fix.sql:413` · lensa `rls-holes`

**Skenario kegagalan:** Any authenticated user of tenant A executes one INSERT into app.user_company_access naming their own user_id and tenant B's company_id. Because company_in_scope() re-reads user_company_access on every subsequent statement, tenant B's estates, users, cost_transactions, budgets, forms, evidence, cert programs and approval requests all become readable AND writable in the same transaction. Every *_tenant policy created in 0014/0015/0016/0017 is derived from this table, so all of them fail simultaneously. verify.mjs:115-117 misses it: it only checks that setting current_company_id=C2 without a grant yields 0 rows, never that the grant itself can be self-issued.

**Perbaikan:** user_company_access is authorization data, not tenant data — app_rw must not write it. REVOKE INSERT, UPDATE, DELETE ON app.user_company_access FROM app_rw and move granting into a SECURITY DEFINER function that verifies the caller is super_admin of the granting company. Additionally narrow the policy to read-only self-inspection: `CREATE POLICY uca_self ON app.user_company_access FOR SELECT USING (user_id = app.current_user_id() OR app.company_in_scope(company_id));` and add a RESTRICTIVE policy blocking writes. Same treatment for app.user_estate_access (see separate finding).

### 7. [HIGH] user_estate_access has no RLS and full DML granted, so a creator can self-grant estate access and nullify 0014's RESTRICTIVE blocks_estate_scope fix

**Lokasi:** `db/migrations/0014_core_fix.sql:364` · lensa `rls-holes`

**Skenario kegagalan:** A 'creator' whose visibility is supposed to be limited to their assigned estates runs one INSERT into app.user_estate_access naming any estate_id (including another tenant's) and immediately sees every block in that estate. The RESTRICTIVE policy that 0014 added specifically to fix audit defect (b) is therefore self-service. The same grant also lets a creator DELETE other users' estate assignments.

**Perbaikan:** REVOKE INSERT, UPDATE, DELETE ON app.user_estate_access FROM app_rw; enable RLS with a SELECT-only policy scoped through app.estates (`EXISTS (SELECT 1 FROM app.estates e WHERE e.id = estate_id AND app.company_in_scope(e.company_id))`), and issue assignments through a SECURITY DEFINER function restricted to super_admin/approver.

### 8. [HIGH] report_definition_fields (created by 0017) has no RLS while its parent report_definitions does — cross-tenant read, write and delete of report definitions

**Lokasi:** `db/migrations/0017_reports.sql:48` · lensa `rls-holes`

**Skenario kegagalan:** Tenant A enumerates the field/KPI layout of tenant B's custom reports (business intelligence disclosure), silently deletes B's report fields so B's reports render empty, or injects fields into B's report definitions. The parent-row protection on report_definitions is cosmetic because the child carries the actual report content.

**Perbaikan:** ALTER TABLE app.report_definition_fields ENABLE ROW LEVEL SECURITY; then a parent-derived policy in the same style as 0014's child policies:
  CREATE POLICY rdf_tenant ON app.report_definition_fields
    USING (EXISTS (SELECT 1 FROM app.report_definitions d WHERE d.id = report_definition_fields.report_id
                     AND (d.company_id IS NULL OR app.company_in_scope(d.company_id))))
    WITH CHECK (EXISTS (SELECT 1 FROM app.report_definitions d WHERE d.id = report_definition_fields.report_id
                     AND app.company_in_scope(d.company_id)));
(the WITH CHECK deliberately excludes company_id IS NULL so tenants cannot edit built-in reports).

### 9. [HIGH] 0014 adds company_id to drone_orthophotos but never enables RLS on it — cross-tenant read and re-tenanting

**Lokasi:** `db/migrations/0014_core_fix.sql:247` · lensa `rls-holes`

**Skenario kegagalan:** Tenant A lists tenant B's drone capture codes, estates and footprint geometry (the footprint column is a polygon — A learns exactly where B's plantations are), then re-points B's orthophoto rows at company A so they appear as A's own map layers. Because 0014 made this a company-scoped table, the missing RLS is a leak the pre-0014 schema did not have.

**Perbaikan:** ALTER TABLE app.drone_orthophotos ENABLE ROW LEVEL SECURITY; ALTER TABLE app.drone_orthophotos FORCE ROW LEVEL SECURITY; CREATE POLICY dro_tenant ON app.drone_orthophotos USING (app.company_in_scope(company_id)) WITH CHECK (app.company_in_scope(company_id)); backfill company_id from estates and make it NOT NULL so a NULL cannot become a global row.

### 10. [CRITICAL] survey_submissions and nursery_inspections still have no RLS, so 0014's submission_values policy and 0017's v_seedling_stock guard nothing at the parent level

**Lokasi:** `db/migrations/0014_core_fix.sql:371` · lensa `rls-holes`

**Skenario kegagalan:** Tenant A reads every field submission and nursery inspection of tenant B, and can flip another tenant's approval_status from 'draft' to 'approved' — bypassing the approval workflow 0014 was built to establish — or zero out B's qty_alive, which directly corrupts B's v_seedling_stock report (0017:142-149 selects the latest approved inspection). Protecting only the child table (submission_values) gives a false sense of coverage; 0013:103-105 said 'the pattern still needs applying to the remaining child tables' and 0014 stopped after four.

**Perbaikan:** ALTER TABLE app.survey_submissions ENABLE ROW LEVEL SECURITY with a policy derived from forms via form_versions (mirror the expression already used in 0014's sv_tenant), and ALTER TABLE app.nursery_inspections ENABLE ROW LEVEL SECURITY with `EXISTS (SELECT 1 FROM app.seed_batches sb WHERE sb.id = nursery_inspections.seed_batch_id AND app.company_in_scope(sb.company_id))` for both USING and WITH CHECK.

### 11. [HIGH] audit_log has company_id but no RLS: every tenant reads the whole money audit trail and can forge entries against other tenants

**Lokasi:** `db/migrations/0016_costing_fix.sql:93` · lensa `rls-holes`

**Skenario kegagalan:** 0016 declares 'Jejak audit pada uang -- wajib' and starts writing every cost_transaction diff to audit_log. Tenant A then reads tenant B's complete financial change history (old and new amounts in the diff jsonb) from a connection that does not even need a user context, and can insert fabricated audit rows attributed to tenant B, destroying the evidentiary value of the log the migration just made mandatory.

**Perbaikan:** ALTER TABLE app.audit_log ENABLE ROW LEVEL SECURITY; FORCE ROW LEVEL SECURITY; CREATE POLICY audit_tenant ON app.audit_log FOR SELECT USING (app.company_in_scope(company_id)); and stop granting INSERT to app_rw — have app.write_audit() be SECURITY DEFINER so only the trigger can append, then REVOKE INSERT ON app.audit_log FROM app_rw.

### 12. [HIGH] 'company_id IS NULL = global' policies let any tenant write global rows and promote its own rows to global (master_items, fertilizer_types, fertilizer_schedules, report_definitions)

**Lokasi:** `db/migrations/0015_master.sql:174` · lensa `rls-holes`

**Skenario kegagalan:** A single creator in tenant A renames or deletes the shared unit-of-measure / cost-category items that every tenant's dropdowns and every budget row reference (0016:116 makes budgets.cost_category_id a FK to master_items), or rewrites the three built-in report definitions from 0017:159-165 that every tenant renders — including repointing RPT-FINANCIAL at a different base_view. It can also plant rows with company_id NULL so they surface in all other tenants' dropdowns.

**Perbaikan:** Split read from write. Keep `company_id IS NULL OR app.company_in_scope(company_id)` in USING, but make WITH CHECK strict: `app.company_in_scope(company_id)` (NULL fails, so a tenant can neither create nor promote a global row). Add a RESTRICTIVE policy forbidding UPDATE/DELETE of rows where company_id IS NULL or is_builtin, and manage global/built-in rows through a super_admin SECURITY DEFINER function or migration only.

### 13. [HIGH] master_types and allometric_coefficients: schema-wide reference tables with no RLS and full DML granted to app_rw

**Lokasi:** `db/migrations/0015_master.sql:166` · lensa `rls-holes`

**Skenario kegagalan:** Any tenant's data-entry user renames or deletes the 10 system master_types seeded at 0015:53-63 — master_items.master_type_id is ON DELETE CASCADE (0015:30), so one DELETE wipes every tenant's dropdown contents for that category. Likewise a tenant can silently alter the allometric coefficients (coef_a/coef_b/carbon_fraction, requires_validation) that all tenants' sequestration numbers derive from, with no audit and no is_system guard.

**Perbaikan:** These are platform reference data, not tenant data: REVOKE INSERT, UPDATE, DELETE ON app.master_types, app.allometric_coefficients FROM app_rw (leave SELECT). If super_admin must edit them from the UI, route it through a SECURITY DEFINER function that checks app_role = 'super_admin' and rejects rows where is_system.

### 14. [BLOCKER] v_budget_vs_actual fans out one budget into N rows for company/estate scopes — budget multiplied, actual divided

**Lokasi:** `db/migrations/0017_reports.sql:126` · lensa `data-integrity`

**Skenario kegagalan:** A finance director opens RPT-FINANCIAL for an estate- or company-scoped budget of Rp 10,000,000 against which Rp 3,000,000 was actually spent across 3 blocks. The view emits 3 identical rows: total budget reads Rp 30,000,000 (3x inflated), each row reports 10% utilisation instead of the true 30%, and is_over_budget stays false even when the summed actual exceeds the budget. Every downstream SUM over this view is wrong by the number of distinct blocks touched.

**Perbaikan:** Aggregate `actual` to the budget's grain instead of joining a block-grain CTE. Replace the LEFT JOIN with a LEFT JOIN LATERAL that sums cost_transactions per budget row and resolves scope explicitly, e.g. `LEFT JOIN LATERAL (SELECT SUM(ct.amount_idr) actual_idr FROM app.cost_transactions ct WHERE ct.approval_status='approved' AND ct.company_id=bg.company_id AND ct.fiscal_period_id=bg.fiscal_period_id AND ct.cost_category_id=bg.cost_category_id AND CASE bg.scope_type WHEN 'block' THEN ct.block_id = bg.scope_id WHEN 'estate' THEN ct.block_id IN (SELECT id FROM app.blocks WHERE estate_id = bg.scope_id) ELSE ct.company_id = bg.scope_id END) a ON true`. Add a regression check to db/verify.mjs asserting one output row per budget row.

### 15. [HIGH] Estate-scoped budgets are charged with costs from blocks in other estates

**Lokasi:** `db/migrations/0017_reports.sql:126` · lensa `data-integrity`

**Skenario kegagalan:** Estate E1 has spent nothing; estate E2 has spent Rp 900,000. RPT-FINANCIAL shows E1 at 90% budget utilisation and E2 at 0%. Per-estate variance analysis is meaningless, and with several estates the same cost is reported against every estate budget simultaneously.

**Perbaikan:** Resolve estate scope to its blocks in the actual-matching predicate (see the CASE expression in the previous finding), and add a guard so an unrecognised scope_type never degrades to 'match everything'.

### 16. [MEDIUM] publish_emission_factor with a backdated (or equal) p_valid_from produces an inverted validity window and silently reassigns history

**Lokasi:** `db/migrations/0014_core_fix.sql:188` · lensa `data-integrity`

**Skenario kegagalan:** A carbon run executed in March 2026 resolved EF-TEST to version 1 (value 1.0) and snapshotted it. An MRV reviewer later backdates a correction by calling publish_emission_factor with valid_from 2025-06-01. Re-resolving the factor for 2026-03-01 now returns version 2 (value 2.0) — the emission figure doubles and version 1 no longer covers any date at all, so the original run cannot be reproduced or explained. The function is the only sanctioned write path (0014:206-209), so this is the normal way factors get published.

**Perbaikan:** In app.publish_emission_factor, before the UPDATE, read the current active row and `RAISE EXCEPTION` if p_valid_from <= current.valid_from. Add `ALTER TABLE app.emission_factors ADD CONSTRAINT ef_window CHECK (valid_to IS NULL OR valid_to >= valid_from)` so the inversion is impossible even outside the function. Handle genuine retroactive corrections as an explicit superseded/restatement path rather than by rewriting valid_to.

### 17. [MEDIUM] budgets.scope_id orphans silently — validate_budget_scope only fires on budgets INSERT/UPDATE, never on deletion of the referenced row

**Lokasi:** `db/migrations/0016_costing_fix.sql:154` · lensa `data-integrity`

**Skenario kegagalan:** A block is deleted (or replaced during boundary cleanup). Its Rp 5,000,000 budget stays in app.budgets pointing at a non-existent uuid and keeps appearing in v_budget_vs_actual / RPT-FINANCIAL with actual 0. Total company budget is overstated by the orphan amount forever, and nothing in the schema can detect it — the trigger only revalidates if someone happens to UPDATE that budget row.

**Perbaikan:** Either give budgets three real nullable FK columns (company_scope_id/estate_scope_id/block_scope_id) with a CHECK that exactly one matches scope_type — which gets ON DELETE enforcement for free — or add BEFORE DELETE triggers on companies/estates/blocks that reject (or cascade) when a budget references the row. Also add a verify.mjs check that no budget has a dangling scope_id.

### 18. [MEDIUM] Rejection reason is unenforced on 9 of the 11 approval-bearing tables — a record can be 'rejected' with no reason

**Lokasi:** `db/migrations/0017_reports.sql:245` · lensa `data-integrity`

**Skenario kegagalan:** An approver rejects a land suitability assessment or a DBH measurement from the mobile app. The row lands with approval_status='rejected' and rejection_reason NULL. The surveyor sees a rejected record with no explanation and cannot know what to fix; concept:187's 'penolakan WAJIB membawa alasan' is enforced on exactly the two tables where it was written by hand and nowhere else.

**Perbaikan:** Add the same CHECK to all nine tables, ideally generated in the same DO loop that creates their policies (0017:296-316), e.g. `EXECUTE format('ALTER TABLE app.%I ADD CONSTRAINT %s_rejection_needs_reason CHECK (approval_status <> ''rejected'' OR (rejection_reason IS NOT NULL AND length(btrim(rejection_reason)) > 0))', t, t)`. Add a verify.mjs assertion that every table with an approval_status column has such a constraint, so future tables cannot skip it.

### 19. [HIGH] validate_budget_scope is SECURITY INVOKER, so its referential check is RLS-filtered: the same INSERT is rejected for one role and accepted for another

**Lokasi:** `db/migrations/0016_costing_fix.sql:133` · lensa `data-integrity`

**Skenario kegagalan:** A creator assigned to estate E1 is asked to enter the block budgets for the whole company. Every budget for a block outside E1 fails with the misleading message 'bukan block milik company ini' — the data is correct, the guard is just blind. Conversely the guard's verdict is a function of session GUCs (app.current_user_id / app.current_company_id / app.current_role) rather than of the data, so it is not a referential-integrity constraint at all: the same row is valid or invalid depending on who writes it.

**Perbaikan:** Make app.validate_budget_scope() `SECURITY DEFINER SET search_path = app, public` (matching app.publish_emission_factor at 0014:174-175) so existence checks see the real table, and keep tenant authorisation where it belongs — the budgets_tenant RLS policy at 0016:196-197. Add a verify.mjs check that the same block-scoped budget INSERT succeeds for both a creator and an approver.

### 20. [MEDIUM] validate_budget_scope accepts a company-scoped budget pointing at a different tenant

**Lokasi:** `db/migrations/0016_costing_fix.sql:137` · lensa `data-integrity`

**Skenario kegagalan:** PT A creates a company-level budget whose scope_id is PT B. The row passes RLS (company_id is PT A) and passes the trigger, so it is stored and reported. Any consumer that groups or labels by scope_id — including v_budget_vs_actual, which exposes scope_id raw at 0017:111 — attributes PT A's budget to PT B. It also breaks the UNIQUE key at 0016:127: PT A can now hold two distinct 'company' budgets for the same period/category by varying scope_id across tenants.

**Perbaikan:** Change the company branch to `IF NEW.scope_id IS DISTINCT FROM NEW.company_id THEN RAISE EXCEPTION …` (or simply always force `NEW.scope_id := NEW.company_id` for scope_type='company' rather than only when it is NULL, as at 0016:136).

### 21. [HIGH] cost_transactions.block_id is not constrained to the transaction's own company — block-level money lands on another tenant's block

**Lokasi:** `db/migrations/0016_costing_fix.sql:77` · lensa `data-integrity`

**Skenario kegagalan:** A user with access to two corporate entities (the multi-tenancy 0014:22-37 explicitly enables) books an expenditure under PT A but selects a PT B block, by mistake or to move cost between entities. v_block_cost_summary and RPT-SUSTAINABILITY attribute the money to PT B's block and inflate PT B's cost/ha, while PT A's ledger total still contains it. Nothing anywhere flags the mismatch.

**Perbaikan:** Add `ALTER TABLE app.cost_transactions ADD CONSTRAINT ct_block_same_company CHECK (block_id IS NULL OR company_id = (SELECT company_id FROM app.blocks WHERE id = block_id))` — not expressible as a CHECK, so use a SECURITY DEFINER BEFORE INSERT OR UPDATE trigger, or denormalise blocks.company_id into a composite FK: add `UNIQUE (id, company_id)` on app.blocks and make cost_transactions reference `(block_id, company_id) -> blocks (id, company_id)`. The composite-FK form is preferable because it is enforced on block UPDATE too. Apply the same pattern to activities.block_id and the five block-scoped tables in 0017.

### 22. [MEDIUM] report_definitions.base_view is unconstrained free text — the 'whitelist' it claims to be validated against has no FK

**Lokasi:** `db/migrations/0017_reports.sql:29` · lensa `data-integrity`

**Skenario kegagalan:** The report runner reads base_view and interpolates it into a query (it cannot be parameterised — it is an identifier). Because the whitelist is documentation rather than a constraint, an app_rw caller stores an arbitrary string and the enforcement point moves from the database into whatever the application remembers to check. The stated defence against injection does not exist at the layer where it was claimed.

**Perbaikan:** `ALTER TABLE app.report_definitions ADD CONSTRAINT rd_base_view_fk FOREIGN KEY (base_view) REFERENCES app.report_allowed_views(view_name)`. Keep report_allowed_views writable only by a migration or a super_admin-gated SECURITY DEFINER function, not by app_rw (0017:321 currently grants app_rw SELECT only on it, which is correct — just add the FK).

### 23. [MEDIUM-HIGH] UNIQUE keys containing a nullable company_id do not apply to global rows — duplicate built-in reports and duplicate global master items

**Lokasi:** `db/migrations/0017_reports.sql:35` · lensa `data-integrity`

**Skenario kegagalan:** Any code path that resolves a report or a dropdown option by code — 'give me the built-in financial report', 'give me the unit KG' — starts returning two rows and picks one nondeterministically, so two users can see different base_views for the same report code, or the same expenditure can be booked against either of two 'KG' master items with different uuids.
